# P1 AI 连续服务停机竞态修复（2026-08-07）

## 结论

全量回归捕获并修复了一个 Windows 命名管道停机竞态。该问题会让 AI 连续服务在已经确认控制端关闭请求后，仍等待内部任务管道唤醒消息超时，造成停机延迟和测试偶发超时；不涉及任务内容丢失或正式提醒核心。

## 根因与修复

关闭线程会设置停止标志，再通过任务管道写入固定内部唤醒消息，让阻塞在 `accept_one` 的主循环及时返回。主循环此前看到停止标志便直接退出，没有确认已经接收的唤醒消息。发送端因此只能等到客户端超时，主循环又在退出前等待关闭线程，形成约一个客户端超时周期的无意义停顿。

修复后，主循环在停止分支先确认已经接收的内部唤醒消息，再退出并回收关闭线程。外部任务消息的认证、提交后 ACK 和失败不 ACK 规则没有改变。

## 验证

- 原始失败：`continuous_service_commits_events_and_exits_through_shutdown_pipe` 在全量回归中等待完成信号 1 秒超时；
- 修复后定向真实执行 20/20 通过，每轮完成时间约 0.05—0.07 秒；
- `cargo test --all-targets` 通过，共 440 项 Rust 测试，另有 3 项按设计忽略；
- `cargo test --all-targets --features runtime-qa,migration-qa,retention-qa` 通过，共 456 项 Rust 测试，另有 3 项按设计忽略；
- `cargo fmt --all -- --check` 与全特性 Clippy `-D warnings` 通过；
- 正式 workspace、Tauri 主程序和 NSIS 安装包均重新构建成功。

该修复缩短的是已授权服务自身的优雅退出路径，不扩大任何工具权限，也不把 Bridge/AI 原型加入当前安装包。
