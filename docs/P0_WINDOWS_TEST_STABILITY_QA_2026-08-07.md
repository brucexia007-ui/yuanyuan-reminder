# P0 Windows 测试稳定性专项记录（2026-08-07）

## 结论

主程序 Rust 库测试进程累计出现过三次间歇性 Windows `STATUS_ACCESS_VIOLATION`。最新一次发生在 2026-08-09 的全量 `cargo test` 末尾；崩溃前输出均为通过，随后主程序库单线程 191/191 通过（1项按设计忽略），再次执行全量 `cargo test` 通过。当前没有崩溃转储或系统错误事件可用于证明根因，因此本专项不把问题宣称为已经定位或关闭。

代码审计确认并修复了一处独立成立的本机安全隐患：读取 Windows Authenticode 签名者证书时，旧实现直接解引用证书链首项，未先通过系统辅助函数验证返回项；失败验证还会在没有状态句柄时请求关闭状态。新实现只关闭非空状态，使用 `WTHelperGetProvCertFromChain` 取得并检查证书项，并限制证书显示名称的最大缓冲区。该修复降低本机 FFI 读取风险，但现有证据不足以断言它就是三次崩溃的唯一原因。

风险状态：**保持开放，已降低并纳入回归。**

## 已检查范围

- 复核了主程序中 Windows 原生调用、全局状态、后台线程、子进程和测试并发点；
- AI 监督线程在应用退出路径中会显式停止、通知辅助进程并回收工作线程，相关启动型测试也显式关闭，未发现与三次崩溃相符的泄漏证据，因此没有加入猜测性的生命周期改动；
- Windows 应用程序事件日志中没有对应测试进程的可用错误记录；
- 当前环境没有产生可分析的崩溃转储，也没有可直接使用的 WinDbg/CDB/ProcDump；
- 前两次输出位置接近连接器工具信任测试，第三次发生在全量测试末尾；Rust并发测试输出仍不能证明实际崩溃线程。

## 压力证据

在修复前后的定位过程中取得以下结果：

- 崩溃后立即以默认并发重跑当时的 180 项库测试：通过；
- 同一批库测试以单线程重跑：通过；
- 本机真实 Codex 签名与包身份定向验证连续 40 次：40/40 通过；
- 完整 180 项库测试以默认并发连续 20 轮：共 3,600 项通过；
- 修复后新增 8 工作线程同时执行真实 Codex Authenticode 与包身份复核的回归测试；该测试连续 20 轮，共 160 次并发复核通过。
- 第三次异常后，当前主程序库单线程 191 项通过，紧接的一轮全量 `cargo test` 通过。

这些结果说明问题低频且当前修改没有引入可重复失败，但不能代替崩溃现场转储。

## 长期回归门

- 保留本机真实 Codex 单次信任适配测试；
- 新增本机存在受管理 Codex 时运行的 8 线程并发信任适配测试；
- 常规整仓、全功能整仓、Clippy、格式和正式构建继续作为每个里程碑的必跑门；
- 若再次出现 `STATUS_ACCESS_VIOLATION`，应优先保存完整测试输出、精确命令、时间和 Windows 崩溃转储，再按崩溃栈决定修复，不以输出邻近测试名代替归因。

## 关闭条件

至少满足以下条件后，才可把风险改为“已关闭”：

1. 取得一次可归因的崩溃栈并修复对应根因，或在固定候选与固定环境下完成约定的长期重复门且产品负责人接受剩余风险；
2. 默认与全功能 Rust 整仓验证持续通过；
3. 本机签名信任并发回归持续通过；
4. 文档明确区分“未再复现”与“根因已证明”。
