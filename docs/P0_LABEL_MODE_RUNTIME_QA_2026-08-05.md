## 3. 本轮证明的边界

- 正式设置入口不是开发实验台，真实 release 主程序能读取、修改并在异常终止后恢复`companionLabelMode`；正常“完全退出”可以结束进程且不新增崩溃事件；
- 默认“需要时显示”和用户可永久选择“纯动作”的界面文案、位置和原生选择控件在当前缩放环境中可见且没有裁切；
- 最新构建激活Windows UI Automation后，WebView内部树可见：`道具标签`是可聚焦`ControlType.ComboBox`且Value为“需要时显示”；`看向鼠标`是可聚焦按钮并支持`TogglePattern=On`；`安静时段开始`拥有独立名称。设置行标题/说明通过`aria-labelledby/aria-describedby`建立程序化关系；
- 从“设置”导航按钮开始连续按Tab，真实焦点顺序为“圆圆动画 → 陪伴亲密度 → 道具标签 → 动画速度 → 看向鼠标”，证明标签组合框进入局部键盘链；
- 本轮没有制造外部任务、修改Hook或把Bridge/AI原型加入安装包，因此没有为了截图伪造运行/失败/等待用户状态；三种模式对真实道具标签的渲染差异目前由生产组件回归测试覆盖，尚缺签名任务链路接通后的窗口级实拍；
- 自动化中曾有强制终止和一段变量错误的脚本，但不能据此排除同一时段的全部`BEX64/c0000409`。后续通过重定向标准错误确认其中真实存在正式包初始化竞态，并完成了下述修复与重新验收；只有修复后精确构建的独立时间窗计入通过证据。

## 5. 正式包初始化竞态复核

- 发现方式：最终打包主程序在窗口创建期间偶发以`BEX64/c0000409`终止；PDB与标准错误回溯显示并非内存越界，而是`AppState`尚未`manage`时，正式前端已经发起设置/今日事项请求，Tauri的状态提取在WebView2系统回调中panic且不能展开；
- 第一层修复：退出事件改用`try_state`，初始化未完成时不再读取全局状态；该修复消除了退出处理本身的panic，但正式包加载真实前端时仍能复现命令与状态注册竞态；
- 最终修复：日志、启动备份、SQLite仓库、活动计时器和完整`AppState`在`Builder`创建配置窗口前准备并`manage`；`setup`只读取已存在状态，应用窗口设置、陪伴运行时、托盘和后台调度。这样正式WebView即使立即请求数据，也不会访问未注册状态；
- 精确正式构建`34EEE814...A905199`先完成1轮独立验收，随后再完成3轮连续验收。四轮均满足：主实例8秒内无提前退出、第二实例退出码0、设置页“完全退出”可由UI Automation调用、主实例最终退出码0；对应独立时间窗内`Application Error / 1000`新增数量均为0；
- 后续任务守望构建暴露日志滚动器在目录不可写时会panic；现已改用可返回错误的构造器并降级为空日志写入，新增不可用日志目录测试。最新精确构建`9FC9FEE7...0BFF9F28`在正常Windows用户权限下完成启动/单实例回归：主实例保持运行、第二实例退出码0、独立时间窗`Application Error`新增数量为0；
- 修复后的Rust全目标测试、`cargo fmt`、严格`clippy -D warnings`、前端20文件/115测试、发布边界检查和NSIS构建均通过。该结论只关闭本次初始化panic，不替代长期稳定性、真实安装/卸载、多DPI、高对比度、Narrator和目标用户验收。
